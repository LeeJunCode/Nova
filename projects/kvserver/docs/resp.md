# RESP 协议参考(v2)实现版

> 官方来源:<https://redis.io/docs/latest/develop/reference/protocol-spec/>
> 本文档不是抄协议原文,而是**结合我们的 kvserver 实现**写的"要实现什么、怎么实现"的协议参考。范围 = RESP2(见 `docs/introduce.md`)。

---

## 1. RESP 是什么

RESP(REdis Serialization Protocol)是 Redis 客户端与服务器之间通信的协议。**客户端把命令编码成字节发过来,服务器把结果编码成字节回过去**,双方按同一套格式收发。

所有通信都是**通过 TCP 的字节流**进行的。TCP 是流,不是"一封封信"——它**不给消息划边界**。所以协议必须靠数据**自己描述自己的长度**,接收方才能从流里准确切出"一条完整消息"。(这就是粘包/半包问题的根源,见 §4。)

## 2. 总体规则(先记这四条,其它全是推论)

1. **行终止符是 `\r\n`(CRLF)**。凡以"行"为单位的帧都以 `\r\n` 结尾。
2. **长度一律按"字节"计,不是字符**。数据里有中文/emoji 时,字节数 ≠ 字符数。`std::string::size()` 就是字节数,直接用。
3. **每种帧都自带长度信息(自定界)**。接收方随时能回答"当前够不够一条完整帧,还差几个字节"。
4. **靠首字节区分帧类型**:`+` `-` `:` `$` `*`,就这五种(见 §3)。

## 3. 五种帧类型(完整定义)

| 类型 | 首字节 | 语法 | 内容里能有什么 |
|---|---|---|---|
| 简单字符串 | `+` | `+<文本>\r\n` | 不能含 `\r\n` |
| 错误 | `-` | `-<错误文本>\r\n` | 不能含 `\r\n`;首词是错误码 |
| 整数 | `:` | `:<有符号十进制>\r\n` | 不能含 `\r\n` |
| 批量字符串 | `$` | `$<长度>\r\n<数据>\r\n` | **数据可以是任意字节,包括 `\r\n`、空、二进制** |
| 数组 | `*` | `*<个数>\r\n<元素1><元素2>...` | 元素是任意帧(可递归) |

逐个拆:

**简单字符串 `+`** —— 短的、人类可读的回复。
```
+OK\r\n
```
收到 `+` 后,读到下一个 `\r\n` 为止就是内容。内容里不许有 `\r\n`。

**错误 `-`** —— 格式上跟简单字符串一样,但语义是"出错了",客户端库把它当异常抛。
```
-ERR unknown command 'foo'\r\n
-WRONGTYPE Operation against a key holding the wrong kind of value\r\n
```
**约定**:错误文本的第一个词是**大写错误码**(`ERR` / `WRONGTYPE` / …),后面跟空格和具体消息。redis-cli 会原样显示。我们只需按这个格式拼对即可(消息文本见 §6)。

**整数 `:`** —— 一个有符号 64 位整数,`\r\n` 结束。
```
:1000\r\n
:0\r\n
:-2\r\n        ← 可以负,TTL 的 -2 就靠它
```

**批量字符串 `$`** —— 一个"自带长度的字符串",这是**最重要的帧**。
```
$5\r\nhello\r\n     ← 长度 5,内容 5 个字节
$0\r\n\r\n          ← 长度 0 = 空字符串(注意后面紧跟一个空行)
$11\r\nhi\r\nbye\r\n ← 内容 11 字节 = "hi\r\nbye"。长度说 11 就是 11,内容里嵌 \r\n 完全合法
```
读法:**先读 `$<长度>\r\n`,再"精确数"长度那么多个字节**,读完**再验证跟一个 `\r\n`**。绝不能在内容里"找 `\r\n"当结尾**——因为内容里可能本来就有 `\r\n`(上面第三个例子就是)。

批量字符串有**两种特殊长度**:
- `$0` = 真正的空字符串;
- **`$-1` = null(空值)**,表示"这个位置没有值"。只有回复会出现,请求不会出现。

> 空字符串和 null 是**两回事**:`$0\r\n\r\n` 是"值是空的",`$-1\r\n` 是"根本没这个值"。GET 一个不存在的键必须回 `$-1`,绝不能回 `$0`。

**数组 `*`** —— 由"个数 + 一串其它帧"组成,元素可以是任意帧(包括数组、包括 `$-1` null 元素)。
```
*2\r\n$3\r\nGET\r\n$4\r\nname\r\n   ← 2 个元素:两个 bulk
*3\r\n+OK\r\n+OK\r\n+OK\r\n          ← 3 个元素:三个简单字符串(元素可以不是同类型)
*0\r\n                                ← 空数组
*-1\r\n                               ← null 数组(回复专用)
```
读法:先读 `*<个数>\r\n`,然后**按个数循环**,逐个读元素帧。个数可能是 `0`(空数组)。

## 4. 请求(客户端 → 服务器):命令长什么样 —— 我们要解析的

**协议里,一条"命令" = 一个顶层数组,数组元素全是批量字符串(bulk)。**

每个 bulk 就是命令的一个"词"。第一个词是**命令名**,后面是**参数**。Redis 把这串词叫 `argv`,词数叫 `argc`(服务器把"数组元素个数"读出来就是 argc)。

```
ECHO hello        → 数组 *2:["ECHO", "hello"]
SET name lee      → 数组 *3:["SET", "name", "lee"]
GET name          → 数组 *2:["GET", "name"]
```

redis-cli 发出的请求就是这种数组形式,而且**命令名发的是小写**(`set`,不是 `SET`)。

### 4.1 逐字节走读:`SET name lee`

redis-cli 敲 `SET name lee`,线上实际是这 32 个字节(我在每个帧头下标了起始位置):

```
*3\r\n  $3\r\n  SET  \r\n  $4\r\n  name \r\n  $3\r\n  lee \r\n
└4B┘    └4B┘   └3B┘ └2B┘  └4B┘  └4B┘  └2B┘   └4B┘ └3B┘ └2B┘
offset 0    4     8    11    13    17    21    23   27    30
```
读取配方(这就是我们 `parse_command` 做的事):
1. 读到 `*` → 是数组 → 读 `*<N>\r\n`,`N=3` = argc = 有几个词;
2. 循环 3 次,每次读一个 bulk:
   - 读 `$<len>\r\n`(如 `$3\r\n`);
   - **精确取** `len` 个字节当这个词的内容(如 `SET`);
   - 验证后面跟 `\r\n`;
3. 结束时游标停在 `*3\r\n...` 的末尾(本例 offset=32),这段就是**一条完整命令**。

解析结果:`argv = ["SET","name","lee"]`,`argc = 3`。**解析层到此为止——它不认"SET 是命令、name 是键"这种词义,词义是后面分发层的事。**

### 4.2 为什么能处理粘包 / 半包

- **粘包**:两个命令连在一起发(`*1\r\n$4\r\nPING\r\n*1\r\n$4\r\nECHO\r\n`)。因为每个命令都以 `*` 开头、长度自述,读完第一条命令游标停在 14(第一个 `*` 之后正好是第二个 `*`),剩下一截是第二条 → 这就是 `parse_commands` 的"榨干循环"。
- **半包**:一个命令被 TCP 拆成两段到达(先来 `*3\r\n$3\r\nSET\r\n$4\r\nna`,后面 `me\r\n` 才到)。读到一半发现**字节不够**,解析器答"HALF(半包)",**什么都不消费**;服务器把这段留在缓冲里,等下次 recv 追加了再重解析。`parse_command` 的状态 `RESP_HALF_PACKET` 就是这个意思。
- **垃圾**:开头不是 `*`、或者 bulk 内容后没跟 `\r\n`、或者数量对不上 → `RESP_ERR`,协议错误。

### 4.3 请求里不允许的东西(遇到 = 协议错误)

- **元素不是 bulk 字符串**(例如 `*1\r\n+OK\r\n`,数组里装简单字符串)→ 错误;
- **嵌套数组**(数组里的元素是 `*` 数组)→ RESP2 的命令只允许一层;
- **`$-1` null 当参数** → 错误(请求里不该有 null);
- 个数 `0`(`*0\r\n`)或负数 → 错误(空命令没法执行)。

(真 Redis 还接受"inline 文本命令"——不用数组、直接打 `PING\r\n`。我们不实现,见 introduce.md。)

## 5. 回复(服务器 → 客户端):我们要编码的 —— 五种帧各什么时候用

**回复可以随便用哪种帧**,由命令语义决定。对照表见 §6,这里先记"哪种帧回什么":

| 回复类型 | 写法 | 典型用在 |
|---|---|---|
| 简单字符串 | `+OK\r\n` | SET 成功、PING 的 `+PONG`、TYPE 的 `+string` |
| 错误 | `-ERR ...\r\n` | 命令名不认识、参数个数不对、值类型不对 |
| 整数 | `:1000\r\n` | INCR/DECR 的新值、DEL 删除个数、TTL 剩余秒、STRLEN/APPEND 的长度 |
| 批量字符串 | `$3\r\nlee\r\n` | GET/ECHO 回一个字符串值 |
| 数组 | `*2\r\n...` | 未来一次回多个值(MGET/LRANGE);元素可混类型、可含 `$-1` |

**最容易踩的两个点**:
1. **空串 vs null**:值确实是空串回 `$0\r\n\r\n`;键不存在回 `$-1\r\n`。
2. **错误码首词大写**:`-ERR ...`、`-WRONGTYPE ...`,后面消息内容跟我们 §6 抄的一致即可(redis-cli 只做显示)。

## 6. 命令 ↔ 回复 对照表(红线包,字节级)

> 表里 argv 是我们 `parse_command` 解析出的词;成功回复给出**它该编码成的确切字节**。这张表 = 你写分发层/编码层时的**规格 + 单测期望**。

**连接类**

| 命令 | arity | argv 例子 | 成功回复 | 边界/错误回复 |
|---|---|---|---|---|
| `PING` | 1 | `["ping"]` | `+PONG\r\n` | 参数个数≠1 → `-ERR wrong number of arguments for 'ping' command\r\n` |
| `ECHO` | 2 | `["echo","hi"]` | `$2\r\nhi\r\n`(回显参数) | argc≠2 → 同上(wrong number…) |

**字符串类**

| 命令 | arity | argv 例子 | 成功回复 | 关键边界/错误 |
|---|---|---|---|---|
| `SET` | 3 | `["set","name","lee"]` | `+OK\r\n` | argc≠3 → wrong number |
| `GET` | 2 | `["get","name"]` | 值存在:`$3\r\nlee\r\n`;值是空串:`$0\r\n\r\n` | **键不存在:`$-1\r\n`(null,不是空串)** |
| `GETSET` | 3 | `["getset","n","v"]` | 返回**旧值**(bulk);旧值不存在则 `$-1\r\n`,然后设置新值 | argc≠3 → wrong number |
| `INCR` | 2 | `["incr","n"]` | `:新值\r\n`;键不存在按 0 计再 +1 → `:1\r\n` | 值不是整数 → `-ERR value is not an integer or out of range\r\n` |
| `DECR` | 2 | `["decr","n"]` | `:新值\r\n` | 同上(非整数错误) |
| `INCRBY` | 3 | `["incrby","n","5"]` | `:新值\r\n` | 增量非整数 → 同上错误 |
| `APPEND` | 3 | `["append","s","x"]` | `:追加后的长度\r\n`;键不存在先当空串 | argc≠3 → wrong number |
| `STRLEN` | 2 | `["strlen","s"]` | `:字节长度\r\n`;**键不存在回 `:0\r\n`**(不是 null!) | — |

**通用 key 类**

| 命令 | arity | argv 例子 | 成功回复 | 边界 |
|---|---|---|---|---|
| `DEL` | ≥2 | `["del","a","b"]` | `:删掉的个数\r\n`(可为 0) | 键不存在算 0 |
| `EXISTS` | ≥2 | `["exists","a"]` | `:存在的个数\r\n` | — |
| `EXPIRE` | 3 | `["expire","k","100"]` | `:1\r\n`(设置成功) | 键不存在 → `:0\r\n`;秒数≤0 等同删键 |
| `TTL` | 2 | `["ttl","k"]` | `:剩余秒\r\n` | **键不存在:`:-2\r\n`;键在但没设过期:`:-1\r\n`** |
| `TYPE` | 2 | `["type","k"]` | 键存在(我们是 string):`+string\r\n` | 键不存在 → `+none\r\n`(简单字符串,不是 null!) |

**通用错误文本(和真 Redis 一致地拼)**:
- 参数个数:命令名一律小写 → `-ERR wrong number of arguments for '<命令名>' command\r\n`
- 未知命令:命令名小写 → `-ERR unknown command '<命令名>'\r\n`
  (真 Redis 在后面还会带参数列表;我们 v1 省略,不影响 redis-cli 识别)
- 类型不对(对非字符串键做 INCR/APPEND 等,以后有非字符串类型时用)→ `-WRONGTYPE Operation against a key holding the wrong kind of value\r\n`

**我们 v1 的已知简化**(真 Redis 支持、我们暂时只做子集,单测里按简化断言):
- `PING` 真 Redis 允许多带一个消息参数并回显(bulk);我们只做无参版,多参报错;
- `SET` 真 Redis 支持 `NX/XX/GET/EX/PX` 等选项;我们只做纯 `SET key value`(正好 3 个词);
- `DEL`/`EXISTS` 真 Redis 支持多键;我们按多键实现(arity ≥2)。

## 7. 与 redis-cli 兼容的两个硬要求

1. **命令名大小写不敏感**:`SET`、`set`、`SeT` 都要认。真 Redis 查表前把 `argv[0]` 转小写。所以我们的**分发层拿 `argv[0]` 去匹配前,先转小写**。redis-cli 发小写,但用户用 telnet 可能打大写。
2. **arity 参数个数校验**:每条命令先查自己"要几个词",`argc` 不符就回 §6 的错误文本,不执行。
